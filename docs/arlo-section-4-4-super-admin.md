# 4.4 Design of Software, System, Products, and Processes

The system design phase focused on process flow, user roles, database structure, interface modules, validation rules, and administrative control. The latest design uses three main actors: Alumni, Administrator, and Super Admin. These actors are separated at the account level so that alumni accounts, administrator accounts, and Super Admin accounts are not stored as one mixed group. Alumni accounts and CSV-imported alumni roster records are stored in the `users` table, regular administrator accounts are stored in the `admins` table, and Super Admin accounts are stored in the separate `super_admins` table.

Alumni use the system to maintain profiles, submit tracer information, view announcements, receive notifications, browse job postings, submit job opportunities for review, and submit feedback. Administrators manage the operational records of the system according to their assigned access role. The Administrator role has full access to the operational admin modules. The Alumni Records Manager role is limited to alumni records and tracer monitoring. The Job Manager role is limited to job posting management and alumni-submitted job opportunity review. The Super Admin is designed for account governance and audit monitoring. Its user interface is different from the regular Admin and Alumni interfaces because it does not include job management, announcement management, feedback management, analytics, or other day-to-day operational modules. The Super Admin interface is limited to administrator account management, alumni account maintenance, and audit log monitoring. Through this interface, the Super Admin can create, view, update, and delete regular administrator accounts, assign or update administrator access roles, remove administrator role access, and edit alumni or administrator account details when correction or account control is required.

The design documents are connected to each other. The Data Flow Diagram shows how information moves between the actors and the system. The conceptual data model identifies the main data objects involved in those processes. The Entity Relationship Diagram then translates those objects into database tables, keys, and relationships. This sequence was used so that the process design first explains the system activities, the data model then identifies the important data objects, and the ERD finally shows how those objects are stored in the Laravel and PostgreSQL database structure.

## 4.4.1 Data Flow Diagram Level 0

The Data Flow Diagram Level 0, also called the context diagram, presents the system as one major process interacting with Alumni, Administrator, and Super Admin. This level does not show the internal database tables; instead, it focuses on the major input and output flows between the actors and the proposed system.

**Figure X. Data Flow Diagram Level 0 of the Web-Based Tracer and Employment Analytics System**

In the Level 0 diagram, alumni provide login credentials, profile updates, tracer data, job opportunity submissions, and feedback. The system returns dashboard content, announcements, notifications, job information, job submission review updates, and profile data. Administrators provide record management requests, job posting actions, job submission review actions, announcement publishing actions, feedback updates, and analytics requests according to their assigned role. The system returns managed records, dashboards, reports, and audit logs. The Super Admin provides account management requests, such as creating administrator accounts, updating administrator account information, deleting administrator accounts, assigning administrator access, and editing alumni account details when needed. In return, the system provides admin account lists, alumni account details, role status, account update confirmations, and activity logs.

## 4.4.2 Conceptual Data Model

The conceptual data model presents the high-level data objects of the system before they are translated into detailed database tables. The main objects are Alumni, Super Admin, Admin, Tracer Record, Job Submission, Job Posting, Feedback, and Announcement. The Alumni object represents graduate users who maintain personal, academic, and employment information. The Admin object represents regular office personnel who manage records and system content according to their assigned role. The Super Admin object represents the separate account-control authority responsible for creating administrator accounts, updating administrator account details, deleting administrator accounts, assigning access roles, and editing alumni account information when account correction is required.

**Figure X. Conceptual Data Model of the Web-Based Tracer and Employment Analytics System**

The model shows that Alumni are connected to Tracer Records because alumni submit employment and graduate outcome information. Alumni are also connected to Job Submissions and Feedback because they can propose job opportunities and send concerns or suggestions to the office. Admins are connected to Job Submissions, Job Postings, Announcements, and Feedback because they review, publish, manage, and respond to these records depending on their assigned access role. The Super Admin is connected to Admin through administrator account management because the Super Admin controls the creation, updating, deletion, and role assignment of administrator accounts. The Super Admin is also connected to Alumni through account editing because it can correct or update alumni account details when necessary.

## 4.4.3 Entity Relationship Diagram

The Entity Relationship Diagram illustrates the detailed database structure used by the system. The latest design separates the three account groups into different tables. Alumni are stored in the `users` table, regular administrators are stored in the `admins` table, and Super Admin accounts are stored in the `super_admins` table. This structure keeps alumni records separate from staff accounts and also separates regular administrative work from Super Admin account-control authority.

**Figure X. Entity Relationship Diagram of the Web-Based Tracer and Employment Analytics System**

The ERD shows that one user can have many tracer records, job submissions, feedback records, notifications, sessions, and user-related audit logs. CSV-imported alumni records are also stored in the `users` table and are marked through `is_batch_imported` until the alumnus completes verification and registration. The `admins` table connects to job submissions, feedback, jobs, announcements, and system logs because administrators review submitted records, manage content, and perform monitored administrative actions according to their assigned role. The `super_admins` table is separate from `admins` and connects to administrator account management because Super Admin accounts can create, update, and delete regular administrator accounts. The `super_admins` table also connects to alumni account editing and system logs so that account-level changes can be traced for accountability.

Together, the Data Flow Diagram, conceptual data model, and Entity Relationship Diagram show how the system moves from user interaction to data storage. Alumni provide tracer and employment-related records, administrators manage and review those records, and the Super Admin governs staff account access through a separate Super Admin account structure. This connected design supports centralized alumni tracer management, employment analytics, controlled administrator access, and accountability within the Alumni Relations and Linkages Office.
